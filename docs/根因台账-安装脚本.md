# 根因台账：Windows 安装脚本六轮红灯（1.1.0）

> 按 Claude 裁定（2026-11-20《Claude裁定-安装脚本重构与诊断策略》）第 3 节第 4 条建立：一轮一个假设，记录现象 → 假设 → 证据 → 改动 → 结果。同一区域两轮不收敛即上升设计层面——本台账的五条最终汇总为一条元根因，并已按裁定完成重构（业务初始化收进应用）。

## 元根因

把「业务初始化」（建管理员、生成密码、写审计）用 **cmd + 内嵌 PowerShell + 内嵌 SQL 三层字符串拼接**实现。每一层都有自己的引号/展开/编码规则，修一处冒一处。下面五条都是这同一根因的不同切面。裁定后的固定规则：**.bat 只做操作系统的事；业务数据只由应用（Java）做；SQL 只出现在 Flyway 与 Java 代码里。**

## 台账五条

### 1. for /f 反引号命令里的转义引号破坏 cmd 引号平衡
- 现象：backup.bat 在真机 cmd 报 `{ was unexpected at this time` 并中断，stop.bat 经 call 连带失败（运行器第 1 轮，28 项失败之一）。
- 假设：`for /f` 回读 backup-status.json 的 PowerShell 正则 `\"([^\"]*)\"` 中转义引号让 cmd 引号配平错乱。
- 证据：失败点定位在 backup.bat:39，同型写法共 5 个文件（backup/restore/apply-patch/rollback/upgrade）。
- 改动：正则中 `\"` 改 `\x22`。
- 结果：第 2 轮起该错误消失，P3 停服备份通过。

### 2. 生成随机密码的 for /f 一行式在真 cmd 下静默产空
- 现象：install 第 9 步「成功」执行但 admin 账号从未创建，密码文件缺失（第 2–3 轮）。
- 假设：生成密码的 RNG 一行式写在 for /f 反引号内，含 `\"` 与花括号，解析失败且不报错，ADMIN_PW 恒为空字符串，后续 `if not "%ADMIN_PW%"==""` 恒假。
- 证据：第 3 轮加诊断后确认 EXISTS 查询能读到 "0"，但 DO_BOOTSTRAP 从未置位。
- 改动：四脚本（install/reset-admin/upgrade/apply-patch）统一改为顶层 PowerShell 命令写临时文件 + `set /p` 回读。
- 结果：密码开始生成（第 5 轮密码文件出现、长度 ≥16 校验通过），但 bootstrap 仍失败——见第 4 条。

### 3. cmd 括号块内 %VAR% 在整块解析时展开（值被「定死」）
- 现象：start.bat 的密码文件清理永不执行；install 第 9 步 `call :gen_password` 与读 `%ADMIN_PW%` 同块时恒读到空（第 4 轮）。
- 假设：同一括号块内设置的变量在块解析时已被展开为旧值。
- 证据：P1-ADMIN-LINES 诊断显示 EXISTS="0" 正确、gen_password 已调用，但紧随其后的 DO_BOOTSTRAP 判定恒假；两条语句拆到块外后行为恢复。start.bat 清理逻辑同病（探针变量同块读写）。
- 改动：install 第 9 步拆为两条顶层语句；start.bat 清理改子例程（call 时重新解析）。
- 结果：第 5 轮密码文件生成、bootstrap 语句开始真正执行（exit code 可见）。

### 4. psql 的 -c 参数不做变量替换
- 现象：bootstrap 的 psql 语句 exit code = 1，admin 仍未建成（第 5 轮）。
- 假设：`crypt(:'pw', …)` 中的 `:'pw'` 未被替换。
- 证据：本地真 PostgreSQL 复现：`psql -v pw=x -c "select :'pw';"` 直接报 `syntax error at or near ":"`，三种写法（:'pw' / :pw / 前置 E 字符串）全失败；运行器 annotation 的 LINE 1 回显同样带未替换的 `:'pw'`。psql 只在文件/stdin 输入时做变量替换，-c 不做——这是文档行为，脚本作者（AI）误以为可用。
- 改动（当轮）：四脚本改走 PowerShell 生成临时 .sql 文件 + `psql -f`；本地验证建号成功、哈希可用 Spring BCryptPasswordEncoder 验过（顺带排除「pgcrypto $2a$ 与 Spring 不兼容」的假设，实测 matches=true）。
- 结果：第 6 轮 bootstrap 仍未确证成功（admin 登录 401，诊断证据不足，见第 5 条）——至此同一区域已远超两轮不收敛，按裁定停止修补、整体重构：**AdminBootstrapRunner 收进应用**，脚本侧 SQL 全部删除。本条与 1–3 条的当轮改动随重构一并作废，但教训保留。

### 5. 诊断通道不可靠：echo 清 errorlevel + 失败条目前缀不匹配
- 现象：两处「假绿/假盲」——install 里 `echo … %ERRORLEVEL%` 之后再判 errorlevel，echo 已把退出码清 0，ADMIN_CREATED 恒为 1；运行器第 6 轮的关键诊断（P1-ADMIN-LINES）没有出现在 annotations 里。
- 假设：前者为 cmd 语义（echo 重置 errorlevel）；后者为 ps1 的 Dump-Tail 触发条件只匹配 'P1b' 前缀，而全局异常记录的是 'FATAL: …'。
- 证据：逐行复读 install.bat 与 windows-verify.ps1 后确认两处逻辑。
- 改动：install 改为 psql 后立即 `set "BOOT_RC=%ERRORLEVEL%"` 并自检 bootstrap 后 admin 行数；ps1 的 FATAL 也触发 P1 日志抓取、grep 图案扩围、admin 登录失败时加打 bootstrap/status。
- 结果：改动已随第 7 轮推送，但裁定到达后该轮定位被重构 supersede；这两条作为**脚本与验证器的通用纪律**保留：关键退出码立即存变量；诊断的触发条件必须覆盖全局异常路径。

### 第 6 条（冒烟档首跑，2026-11-20）

- 假设：install.bat 在代码页 936 或中文路径下某一步出错（候选：脚本内 echo 中文与代码页冲突、路径拼接、PG 初始化在中文目录下失败）。
- 证据（第二轮取到，run 44723832326 冒烟注释，initdb 输出原文）：install.bat 正确走完路径警告、配置生成、端口设置，停在「Initializing PostgreSQL data directory - UTF8, ICU locale zh-CN ...」；随后 initdb 报错 `invalid binary "C:\ibwork-smoke\?? ??\iteration-board-offline-1.1.0\runtime\pgsql\bin\initdb.exe": No such file or directory` 与 `initdb: error: could not start process for command ...`。即「迭代 平台」四字在 initdb 自举子进程的路径里被替换为 `?? ??`。

### 第 8 条（档 3：P13 迁移脚本的 PowerShell 模块脆弱性，2026-11-20）
- 现象：run 44746018336 档 3 中 P13 迁移导出/导入失败：导入日志报 `Cannot find an overload for "ExtractToDirectory" and the argument count: "3"`，位置 `C:\program files\powershell\7\Modules\Microsoft.PowerShell.Archive\Microsoft.PowerShell.Archive.psm1:1162`；导出日志中 Get-FileHash 为 CommandNotFound。
- 根因（已证实）：产品 .bat 以 `powershell.exe`（5.1）调用 Expand-Archive / Get-FileHash 等模块 cmdlet；当调用方会话是 PowerShell 7（如 CI 的 pwsh 7 宿主、或用户在 PS7 终端里运行 .bat）时，子进程继承被污染的 PSModulePath，5.1 误加载 PS7 的模块实现——Archive 模块调用了 .NET Framework 不存在的 ZipFileExtensions 三参数重载，Utility 二进制模块则直接加载失败。属产品脚本的真实健壮性缺陷，非纯 CI 环境问题（用户从 PS7 终端跑迁移/补丁脚本会同样中招）。
- 改动：packaging/windows 三脚本去模块 cmdlet 依赖——migrate-import.bat 解压改 .NET Framework 的 [IO.Compression.ZipFile]::ExtractToDirectory（2 参）；apply-patch.bat、migrate-export.bat、migrate-import.bat 的哈希计算改内嵌 Get-Sha256 函数（[Security.Cryptography.SHA256] 流式计算），在 5.1 下不依赖任何模块加载。check-bat 通过。
- 结果（第二轮验证，run 44752094272）：模块脆弱性已消除——导出全程绿，导入的解压、manifest 哈希校验、数据库恢复、设置应用均执行完；但导入后「启动应用」一步失败（B 机 meta 不通、标记账号无法登录），属新暴露，定性见下条追加。
- 追加定性（2026-11-20 晚，用户取回运行器证据包后定性）：**根因——migrate-import.bat「应用导出设置」环节把 B 机 config/application.yml 第 8 行（server.port 行）改成了字面量 `$118080`**。证据原文（p13b-IterationBoardApp.out.log）：`Application run failed`、`while scanning a simple key`、`in 'reader', line 8, column 1: $118080`、`could not find expected ':'`，失败点在 SpringApplication.prepareEnvironment 阶段解析 YAML——故应用日志干净、服务起不来、meta 不通。机制：改写命令把替换串拼成 `'$1' + $p`（$p=18080），得到 `$118080`；.NET 正则替换语法中 `$` 后的连续数字被整体解析为一个分组号，分组 118080 不存在时整串按字面量写入，而被替换的是整行匹配（含 `port:` 前缀），第 8 行遂只剩 `$118080`。同命令的 AI 取值替换有同类风险：值以数字开头会与 `$1` 粘连成大分组号；值含 `$&`、`$$` 等替换元字符会被二次解释（本地复现中 api-key 被改写成混入整行匹配文本的乱码）。本地以非默认端口 19090 复现出 `$119090`，与证据形态完全一致。导出侧 migrate-export.bat 的密码置空替换为 `'$1""'`：`$1` 后是引号而非数字、且原密码值不进入替换串，**不受此类影响**（已核查）。
